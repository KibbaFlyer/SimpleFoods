# HealthKit decisions and acceptance gates

Evidence date: 2026-10-10. Bounded specification spike for A05/A16/A17/A19. No repository edits, builds, license acceptance, Health mutations, or device verification performed. All numerical cases are synthetic. Policies below are implementation recommendations, distinguished from Apple guarantees.

## Evidence register

- Apple authorization: https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data — read denial is intentionally indistinguishable from no readable data; share permission is per type; successful permission request is not a grant of every permission.
- Apple statistics: https://developer.apple.com/documentation/healthkit/executing-statistical-queries — cumulative statistics and calendar-derived boundaries. https://developer.apple.com/videos/play/wwdc2022/10005/ recommends cumulative statistics collection for expenditure. Exact multiple-source energy behavior still requires physical-device comparison; do not infer a universal deduplication algorithm from step-count evidence.
- Apple identity: https://developer.apple.com/documentation/healthkit/hkmetadatakeysyncidentifier — greater version replaces existing same identity. https://developer.apple.com/documentation/healthkit/hkmetadatakeysyncversion . Public text inspected does not spell out the same-version save callback/result contract; do not invent it.
- Apple deletion: https://developer.apple.com/documentation/healthkit/hkhealthstore/delete(_:withcompletion:)-17hzm — deletion limited to app-created samples; revoked share permission prevents deletion; object-array deletion is all-or-nothing and missing objects fail. Deleted-object history is temporary.
- Apple nutrition hierarchy: https://developer.apple.com/documentation/healthkit/nutrition-type-identifiers — describes fibre/sugar beneath carbohydrate, but does not settle a source-specific chemical definition or polyol crosswalk.
- EU 1169/2011 Annex I: https://eur-lex.europa.eu/legal-content/en/ALL/?uri=CELEX%3A32011R1169 — metabolisable carbohydrate includes polyols; fibre defined separately; salt equivalent uses factor 2.5. This is the basis for EU-label handling, not evidence of Apple's definition.
- Apple limited history: https://developer.apple.com/documentation/healthkit/hkhealthstore/getearliestauthorizedsampledate(for:completion:) — beta page, type-specific earliest dates; missing dictionary entry is full OR denied, never proof of full access.
- Local primary SDK evidence: /Applications/Xcode.app/Contents/Developer/Platforms/iPhoneOS.platform/Developer/SDKs/iPhoneOS.sdk/System/Library/Frameworks/HealthKit.framework/Headers/HKHealthStore.h lines 158–159 declares earliest-date method iOS 27.0; HKMetadata.h lines 148/157 declares sync keys iOS 11.0. These are inspected SDK declarations, not minimum deployment recommendations. Use compile-time SDK checks plus runtime availability, and recheck shipping SDK. No exact OS floor claimed for other APIs in this spike.
- Apple backup: https://support.apple.com/en-us/108770 distinguishes device snapshots from syncing; downloaded app data normally participates. https://support.apple.com/guide/iphone/back-up-your-health-data-iph11f1eb698/ios describes Apple's Health synchronization, separately. https://developer.apple.com/app-store/review/guidelines/#health-and-health-research prohibits app storage of personal health information in iCloud. The text does not expressly resolve every OS-backup case; release review must not invent an exception.

## Read contract

Use one .cumulativeSum query per active and basal type with the same explicit calendar/time-zone interval, preferably collection buckets anchored to day boundaries. Never sum separate-source totals, raw sample arrays, or workouts into active energy. Do not calculate expenditure from dietary data. Trust HealthKit's aggregate rather than implementing a new overlap merger. Label result as reported expenditure, with successful-fetch time and coverage caveats.

Availability is separate from read-result state: unsupported/unavailable, restricted/error, notRequested, loading, noReadableData, value(value, window, fetchedAt, coverage), stale(previous, error), deferredLocked. Do not expose readDenied as an inferred state. Empty sum is noReadableData; a returned real zero quantity may be zero. Write authorization status must never stand in for read access. Keep independent states for active/basal; total only when both contain valid matching-window quantities. Two available components do not prove whole-day physiological completeness. Today's window ends at now and says so far. Retain stale values with an explicit timestamp after lock/error, not a freshly stamped cache.

For limited history on supported SDK/OS, clamp each type separately and mark truncated coverage. A type missing from earliest-date dictionary remains fullOrDeniedUnknown. If components have differing truncation, do not show their sum as a full-day total. On older OS omit introspection gracefully. No Watch means no promise of data, not categorical Health unavailability. Day boundaries use calendar addition, including 23/25-hour DST days.

## Nutrient mapping policy

Maintain independent calculation completeness, semantic mapping status, and per-type write authorization. Export eligibility requires all three plus valid finite nonnegative quantity and supported units. Unknown or trace-without-number is never numeric zero. Complete nutrient totals require known contributions from every consumed component. Derived quantities carry evidence and conversion version.

Approve energy→dietaryEnergyConsumed (kcal via largeCalorie), protein→dietaryProtein (g), total fat→dietaryFatTotal (g), and sodium→dietarySodium (mg), where source definitions are documented. Saturated fat requires a complete compatible total-fat parent. Sugar/fibre have named identifiers but first release should gate their export while carbohydrate parent semantics remain unresolved, unless an explicitly reviewed standalone-export policy is accepted (Apple recommends parent totals for general nutrition apps). Other micronutrients remain individually blocked pending source/unit review.

EU-label carbohydrate export is BLOCKED: preserve EU definition and polyol/fibre evidence; do not simply write EU carbohydrate, add fibre, subtract fibre, subtract polyols, or infer missing fractions. Apple hierarchy alone does not establish a settled transform. Even a source marked total carbohydrate needs documented provenance and a reviewed crosswalk before export. Other approved nutrients continue as partial export. Energy should use supplied authoritative energy; do not replace label energy with 4/4/9, which ignores other contributors.

Salt grams / 2.5 * 1000 gives sodium mg. If salt and sodium describe the same record, choose a single authoritative sodium representation, retain the alternate as evidence, and flag conflicts. Never add them. Label-derived sodium is a derived value, not a separate intake.

## Durable export protocol

Persist diary UUID, meal UUID, nutrient identity, desired event revision, immutable payload hash, sync version high-water mark, expected Health UUID(s), operation ID, attempts/error, and desired presence/absence. Stable identity = namespace + diary UUID + meal UUID + Health type identifier; never regenerate diary UUID on restore. One meal total per nutrient, no component exports/correlations in v1. Minimal metadata; same eating instant for start/end, subject to real-device validation.

Local save/edit/delete and outbox change are one DB transaction. Worker is serialized per meal. Before issuing each operation compare current desired revision; after awaiting Health recheck before marking success. A stale completion must not overwrite newer state; schedule reconciliation of latest state. Payload changes require greater persisted sync version, including eating-time changes. Category-only edits need not change Health payload. Retries retain exact identity/version/payload, not a new random identity or version merely because transport failed.

Apple documents greater-version replacement. Same-version retry is a required integration gate: save once, lose local acknowledgement, repeat exact payload/version, inspect app-owned samples and callback behavior. Never equate save callback with proof that a restored stale version is current. Query app-owned identity and compare returned version/payload; if indeterminate preserve attention state. Advance version only for a new desired payload or deliberate repair after reconciliation. Persist allocated version before issuing write. Crash after successful Health save before ledger commit must converge by inspection/retry. No guarantee across Health and SQLite transactions exists.

Known→unknown, semantic eligibility loss, and local deletion require removing old exported nutrient, preserving tombstone until verified absent. Deletion is own source + exact sync identity (plus stored UUID when useful), never date-range-only or matching calories/name. Empty matches are already absent; do not call object-array deletion with []. Missing-object deletion error triggers re-query. Revocation yields cleanupBlocked and warning that old value may remain. Keep cleanup ledger even if diary is erased. Turning export off pauses new writes; cleanup semantics must remain explicit. Never delete and recreate merely to update a known quantity; greater-version replacement avoids a preventable gap.

Per nutrient: notSelected, blockedSemantic, blockedIncomplete, pendingUpsert, pendingDelete, inFlight, confirmed(version/hash), retryable, cleanupBlocked, reconciliationRequired, externallyRemoved. Per-meal UI derives Off/Pending/Exported/Partly exported/Needs attention from these; success for energy cannot hide denied protein or blocked carbohydrate. Finished exports are not periodically replayed. Detectable user deletion sets externallyRemoved and requires deliberate repair; deleted-object retention is not an eternal tombstone service.

## Restore and backup

Default every restored export intent to reconciliationRequired and pause worker. An old backup's high-water mark cannot prove no newer sample or deletion exists. Query owned identities, compare versions and payloads, and reconcile only with evidence. A newer existing version must never be overwritten by stale restored content. Absence can mean deliberate deletion; do not automatically resurrect. Losing tombstones after reinstall is fundamentally not solved by sync identifiers. If uncertainty persists, restore locally and require explicit historical export/repair preview. Preserve imported diary identity, detect repeated backup ID/content digest, and never merge active diaries in v1.

CloudKit is app-managed cloud storage/sync. iCloud Drive document export is another cloud path. OS iCloud Backup is a device snapshot mechanism, and Apple's Health iCloud sync is its own system facility. These are distinct and must not be advertised interchangeably. Recommend excluding private diary, Health cache, indexes, ledgers and temporary exports from OS backup pending release-policy resolution; implement isExcludedFromBackup on containing protected directories and verify sidecars/new files. Public catalogue/cache is reconstructable. Encrypted local user export requires reviewed encryption and destination policy; encryption does not itself prove iCloud storage is permitted. Do not claim exclusion prevents every user-initiated computer copy.

## Plan flaws / required refinements

1. Limited-history API needs concrete SDK/availability gate: installed header is iOS 27, web page beta; baseline iOS 18 cannot call unconditionally.
2. Same-version retry and stale-completion behavior are underspecified; greater-version replacement alone is insufficient to prove all retry/restore acceptance.
3. No local-only scheme can discover all deletions made after an old backup. Keep restoration paused when evidence is insufficient.
4. Sugar/fibre parent export policy must be explicit while carbohydrate is blocked; table entries alone are not approval.
5. Backup exclusions, OS snapshots and CloudKit must have distinct implementation and user copy; current plan defers a necessary policy decision.
6. 'Both components available' must also require matching coverage windows; availability does not establish complete measurement.
7. App-controlled language applies to app strings only. Purpose strings are bundle-localized, while OS authorization sheets, keyboards, Settings, Files and Health follow system decisions; acceptance must record mismatched-language device behavior rather than promise overrides.

Release gates: focused fake state-machine fixtures below; shipping SDK compilation after license is handled by its owner; signed physical-device test for permissions, energy overlap, timestamp samples, same/lower/higher versions, revoke/delete and crash windows; resolved backup policy; documented nutrient-specific crosswalk. No simulated test qualifies as physical-device evidence.

Atomicity clarification: installed HKHealthStore.h documents that when saving multiple objects, if any cannot be saved, none are saved. Preserve that batch guarantee; it does not create a transaction spanning HealthKit and local SQLite. A per-nutrient worker intentionally isolates permission failures by issuing individual saves. Same-version retry remains a device acceptance gate rather than an asserted undocumented callback outcome; before replay after an ambiguous result, query the exact app-owned identity and version, acknowledge matching payload, defer on uncertainty, and only retry unchanged payload when reconciliation permits it.
