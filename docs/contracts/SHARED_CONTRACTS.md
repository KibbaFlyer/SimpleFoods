# Shared contracts — reviewed v0.1 baseline

10 October 2026. Integration review accepted this domain/wire baseline; the first bounded implementation is recorded in [implementation status](../IMPLEMENTATION_STATUS.md). The explicitly listed Health, source, and device gates remain open. Synthetic fixtures are not production food evidence. Health adapter behavior is constrained by the [reviewed Health decisions](../research/HEALTHKIT_DECISIONS.md) and still requires device evidence. Source permission decisions belong to D01.

## 1. Ownership and dependency graph

Domain has immutable value types and validation; Nutrition depends on Domain; Catalog and Persistence implement Domain repositories; Search depends on resolved projections; HealthIntegration depends on Domain and a narrow Health gateway. Localization supplies formatting, not arithmetic. Features call services. Composition in the app target owns lifetimes, dependency injection, clock, zone provider and serialized private writer. No Domain import of SwiftUI, GRDB or HealthKit.

A01 → A02/A05/D02; A02 → A04/A06/A07; A05+A06+A07 → A08; A08 → A09/A10; A05+A07+A08 → A11/A12; A11+A16 → A17; A07+A08+A09+A17 → A19. D01 independently gates source ingestion/distribution.

Minimum deployment target iOS 18; no unguarded newer API. Do not pin GRDB master. Integration review deferred dependency selection from A02 to A06/A07 because the shell and nutrition core require no database dependency. Before persistence integration, choose an exact stable tag/commit, archive its Package.swift/toolchain requirements, lock it, build minimum-target simulator and device, and verify migrations/FTS5/file-protection behavior with the selected SDK. The upstream master manifest inspected during research declares iOS 13 and Swift tools 6.1; this supports plausibility, not compatibility of an unchosen release. [Primary manifest](https://raw.githubusercontent.com/groue/GRDB.swift/master/Package.swift).

## 2. Representation and identity

All persisted contracts carry schemaVersion. Separate catalogueGenerationID, packVersion, foodRevision, overlayRevision, personalFoodRevision, eventRevision, calculationVersion, userChangeSequence, and Health syncVersion. Never compare different revision domains. Private revisions are positive signed 64-bit integers, strictly incremented on successful semantic edits, with overflow a hard validation failure. Catalogue revisions are opaque immutable strings. UTC instants use integer Unix microseconds; JSON fixtures may use offset-qualified ISO 8601. Decimal quantities/nutrients use finite nonnegative decimal strings in portable storage; arithmetic uses decimal precision without intermediate display rounding. Reject unsupported precision/range rather than overflow or silently truncate. A05 must freeze decimal limits before implementation.

FoodID is a tagged identity: catalogue(namespace, opaqueRecordID), or personal(UUID). Namespace is registered and immutable; source record IDs are escaped, not interpreted as filenames. An internal registry may assign IDs where upstream IDs churn; reviewed rekeys are explicit alias maps, never name/barcode matching. Revisions identify immutable records; namespace+ID+revision uniquely identifies bytes/semantic content. Food kind: ingredient, product, recipe, savedMeal. Lifecycle: active, retired, hiddenPersonal. Archived revisions remain resolvable through pins. Barcodes are strings preserving zeros and may map to several variants requiring disambiguation.

Description fields: names and aliases keyed sv/en/de or source language; brand optional; preparation enum raw/cooked/drained/frozenAsSold/prepared/other with source qualifier; category IDs; salesCountries set of ISO country codes; manufacturingCountries and ingredientOrigins as independently evidenced values; brandCountry and cuisineCountry separate. Each claim has provenance reference. Absence is unknown, never an inferred country. User free text has authorLanguage and is never translated automatically.

Provenance: providerID, sourceRecordID, sourceURL, upstreamVersion, retrievedAt, sourceLanguage, licenceReference, transformationVersion, reviewStatus, and optional evidence/derivation inputs. Pack build archives raw values/units separately; normalized fields link to them. Source permission approval is an input to pack validation, not assumed from physical separation.

## 3. Nutrition and quantity crosswalk

NutritionProfile: profileRevision, basis(quantity > 0, unit g|ml|definedPortion), preparation, nutrient map, optional density(g/ml > 0 with evidence), portion definitions, provenance. Defined-portion basis requires its own stable portionID and explicit equivalence or an exact consumed multiple of that same definition. Each Portion has stable ID, localized optional label, equivalent g and/or ml, measured|estimated, evidence. If both equivalents exist their relationship must agree with explicit density; conflicting conversions fail validation. Missing label is renderable with a generic localized label.

| Nutrient key (definition immutable) | Canonical unit | Display/export policy |
| --- | --- | --- |
| energy.declared | kcal | kJ display = kcal × 4.184; preserve original source energy; no default macro estimate |
| protein | g | Direct amount |
| carbohydrate.euAvailable | g | Separate from total carbohydrate; export mapping gated |
| carbohydrate.total | g | Separate source concept; no automatic equivalence |
| fat.total; fat.saturated; sugars; fibre | g | Separate overlapping concepts, never all summed as mass |
| salt.equivalent | g | EU salt representation |
| sodium | mg | Prefer direct evidence; alternatively salt g × 400, derived, never added to direct sodium |

NutrientValue is a tagged union: known(value > 0), knownZero(value 0), unknown(reason), trace(optional exclusive upper bound and unit), derived(value >= 0, methodID, inputs, assumptions). Unknown/trace have no invented point value. Derived exact conversion remains complete if inputs complete; approximation carries estimated=true. Uncertainty may be a documented interval, never a substituted mean. Explicitly cleared nutrient resolves to unknown(userCleared), distinguishable in overlay history from inherited unknown. Nutrient definitions and canonical units are part of IDs, not localized labels.

ConsumedQuantity: positive decimal and unit g|ml|portionCount|servings with portionID where needed. Zero amount is removal; do not keep zero diary components. Negative/nonfinite invalid. Conversion requires matching basis, explicit portion equivalence or food-specific density; no default ml↔g. Scaling factor = consumed reference quantity / basis quantity. NutrientTotal contains knownSubtotal, completeness complete|incomplete|traceBounded, estimated flag, missing component IDs/reasons and optional bound. Any positive-quantity unknown makes that nutrient incomplete; trace without exact amount blocks exact export. Known-zero is complete. Export policy for approximations must be reviewed by Health owner; incomplete subtotal never exported as complete. Aggregate components once; recipes are containers, not extra intake.

Carbohydrate gate: D03–D05 preserve actual source definitions and A05 must record source→canonical→Health mapping with primary evidence. Neither adding fibre nor sending EU available carbohydrate to Health is authorized merely by a matching field name. Until reviewed, omit carbohydrate export with explicit unsupportedDefinition reason; valid other nutrients continue.

## 4. Override semantics and conflicts

Overlay(target FoodID, schemaVersion, revision, acceptedBaseRevision, updatedAt, operations). Each field operation carries accepted base value fingerprint/revision: inherit means no operation, set(value) means explicit replacement, clear means explicit absence. Reset removes that operation and resolves against CURRENT base. Blank optional text, explicit absence, numeric zero and unknown nutrition remain distinct; required display name cannot clear without another fallback. Per-language names are separate paths. Clear collection yields empty collection, not inheritance.

Nutrition override stores acceptedBasis and acceptedProfileSnapshot plus nutrient operations. If current basis/portion equivalence is compatible, inherit unedited nutrients from current base and apply edited nutrients. Compatibility means same dimension and exact explicit conversion with matching definition/preparation; absent density is incompatible. If basis changes incompatibly, keep the ENTIRE accepted effective personal profile usable and mark needsReview(basisChanged); do not combine current numbers with old operations. Resetting a single nutrient during this conflict requires a previewed choice: retain accepted profile, adopt complete current profile and discard conflicting nutrient operations, or provide an explicit validated conversion. Full profile set is atomic: basis, all supplied nutrient values (omitted = unknown), density and relevant portions change together. Changing only basis is rejected. This resolves the tension between per-field reset and coherent nutrition basis.

Simple source-value drift retains edits and adds informational sourceChanged with before/current/personal values. Structural conflicts retain last accepted resolvable effective record and issue review diagnostics. Catalogue changes never mutate personal values.

Recipe component operations are keyed componentID: setAmount, replaceReference, remove, addPersonalComponent(UUID). Order is a separate ID list. Reordering never redirects an edit. An edited source-removed component survives as a personal component with its retained pin; an unedited source-removed component disappears in future inherited recipe resolution. Unresolvable dependency retains last accepted recipe snapshot and needsReview. Reset operations restores current base recipe for FUTURE logs only.

## 5. Recipes, reusable combinations, and snapshots

Recipe definition: FoodID/revision, components(componentID, FoodID, accepted effective pin, quantity), servings > 0, optional measured finishedYieldG > 0, calculationVersion, preparation assumptions. No recipe or savedMeal references inside recipes in v1. Ingredient total / servings gives per serving. Ingredient total × eatenG / finishedYieldG gives mass portion; absent yield rejects mass logging. Water loss does not change total nutrients by itself. Retention/discard modelling deferred; label approximations rather than invent coefficients.

SavedMeal: components and pins, optional explicit preferred category; no cooking-yield transform. Selecting a recipe into a saved meal expands it into a self-contained pinned leaf snapshot with selected recipe amount and original lineage; no live nested reference. Personal recipes/combinations always retain full effective dependency pins, including overlay revision and normalized profile, so deleting an overlay or source pack cannot change them. Refresh produces review diff and new personal revision only on acceptance.

MealEvent: UUID, eventRevision, diaryIdentity UUID, eatenAt, recordedZoneID (IANA), recordedUTCOffsetSeconds, recordedLocalDate (Gregorian YYYY-MM-DD), selected wall time and fold where applicable, category breakfast|lunch|dinner|snack, categoryMode automatic|manual, components, totals, createdAt, updatedAt, deletedAt optional. Components each have UUID and immutable snapshot: origin IDs/revisions, catalogue generation, effective name and author language, profile/portion and conversion evidence, original selected quantity, resolved quantity, totals/status, full leaf calculation inputs or retained pin reference, calculationVersion. Snapshot retains enough information to rescale without catalogue lookup. Snapshot content is immutable; editing creates a new event revision preserving prior revision for rollback/audit according to A07 retention policy.

Edit opens stored snapshot. Quantity changes scale stored inputs; replace/explicitRefresh resolves new data. Duplicate gets new meal/component UUIDs and entered time, using original snapshots by default. Category-only edit increments event revision but need not rewrite identical Health payloads. Future eating time persists a draft; explicit confirmEaten is needed to commit. Draft cancellation has no Health intent.

## 6. Time policy

Persist actual instant and originating local date/zone. Device zone changes do not regroup old diary entries. Explicit time edit recomputes local date using selected zone and creates a revision. Wall-time input in a DST gap returns nonexistentLocalTime with next-valid suggestion, requiring user selection; ambiguous fold requires earlier/later selection or retains an explicit offset. No silent normalization. Default category windows use selected wall clock, half-open minutes: [05:00,11:00), [11:00,15:00), [17:00,21:00), remainder snack. Manual choice survives time edits. Windows are minute ranges on [0,1440); split overnight windows before overlap validation.

Health energy day request explicitly supplies Gregorian date and comparisonZoneID. Use Calendar-derived start and next day start; interval [start,end), never 86,400 seconds. UI day comparison zone defaults to current device zone but must be visible when it differs from recorded meals; a day with meals recorded across zones shows mixed-zone approximation. Diary totals still use recordedLocalDate. Apple exposes calendar date intervals via [Foundation Calendar](https://developer.apple.com/documentation/foundation/calendar/dateinterval(of:for:)); exact implementation and DST fixtures require A11 validation.

## 7. Stores and activation protocol

Catalogue: immutable source packs plus manifest (generationID, pack IDs/versions, schema/read compatibility, upstream versions, counts, SHA-256 per file, provenance/licence artifacts, revision maps, references). Private DB: overlays, custom foods/revisions, pins, drafts, logs/snapshots, settings, activeGenerationID, activation journal, changeSequence, Health desired/observed ledger and outbox. Derived index/cache may contain private text; protect/exclude from backup like private DB. Health cache is optional/rebuildable. No private information enters public pack builds.

One serialized private writer; reads use consistent snapshots. Meal save acquires a retained catalogue generation lease plus private read versions, resolves everything, then commits only if involved overlay/personal revisions remain unchanged; stale inputs return staleRevision for re-resolve. Transaction inserts event, its revision, Health desired intents and durable changeSequence together. Retain leased generation until transaction ends. Activation can publish a newer generation meanwhile; save remains consistently old.

Activation: stage outside active files; validate all compatibility/checksum/reference/rights gates; retain necessary dependencies in private protected pins as permitted; construct new index tagged generationID+overlayChangeSequence; catch up index deltas or use DB search fallback; transaction records prior/new generation, status committed, and changes activeGenerationID. Files are durable before pointer commit. Recover by verifying pointer targets and journal; old generation remains until no leases and recovery rollback need. Failed staging leaves prior pointer unchanged; never revert unrelated private edits. Overlay changes after index build are fed through durable change sequence or search falls back until current. Cross-file operations are not claimed as one SQLite atomic transaction.

## 8. Service contracts

All commands have operationID UUID and expected revision where editing. Repeating same operationID/payload returns original result; different payload with same ID is operationConflict. Query cancellation has no mutation. Command cancellation before commit returns cancelled; after commit returns committed receipt even if caller disconnects, retrievable by operationID. Every successful mutation emits durable changeSequence, affected IDs/revisions and reason; observers can reload from sequence, notifications carry no private text. Multi-process access is out of scope; A07 owns SQLite integrity, migration and file protection.

Common errors: invalidInput(field,reason), unsupportedSchema, unsupportedDefinition, missingConversion, missingYield, unresolvedReference, staleRevision(expected,actual), structuralConflict(reviewID), notFound, retiredForNewSelection, incompatibleCatalogue, checksumMismatch, sourceNotApproved, storageFull, protectedDataUnavailable, corruptStore, cancelled, operationConflict. Errors contain localization keys and safe parameters, never leaked diary payloads. Retired references can resolve for existing pins; new selection hides by default.

## 9. Health desired-state model — provisional

Identity = persistent diaryIdentity + mealUUID + Health nutrient identifier, encoded deterministically without private text. Ledger key is this identity; retain after meal deletion. desiredGeneration increases whenever desired payload/absence changes; sample syncVersion is persisted monotonic and never derived solely from event revision. DesiredState is present(amount, canonical export unit, eatenAt, payloadHash, policyVersion) or absent(reason deleted|unknown|ineligible|explicitCleanup). ObservedState: unknown, confirmedPresent(sample UUIDs, version/hash), confirmedAbsent, externallyMissing. Separate local desired intent from observed Health state.

Outbox: operationID, ledger key, desiredGeneration, action reconcile, status queued|leased|retryWaiting|blocked|succeeded|superseded, lease token/expiry, attempts, nextAttemptAt, lastSafeError. Reconciler serializes one identity and checks newest desired generation before and after external I/O. Stale completion may update observed evidence but cannot mark newer desired state synchronized. Persist intent before Health I/O; after crash reconcile same stable identity/version, not a fresh UUID. Retryable: locked/transient; blocked: write authorization/unsupported type/restore ambiguity; superseded job never restores obsolete value. Unknown→absent requires removal of former app-owned sample, not omission alone.

Export off pauses new creation/replacement and does not request deletion of existing history. Explicit meal deletion/known→unknown cleanup obligations remain durable; whether cleanup executes while export off requires Settings copy and parent/Health review. Enabling uses future committed meals by default; historical export explicit preview. Restore imports identities/ledger but sets reconciliation hold; old versions and post-backup deletions require explicit conflict resolution. Completed entries missing externally are not blindly recreated. Aggregate UI derives pending/partial/exported/needsAttention from per-nutrient eligible and observed states, separately reports unsupported nutrients. Exported means confirmed for current desired state, not merely queued.

Acceptance target: 500→600 kcal same identity higher version results in one 600 kcal sample, not 1,100; retry same desired generation is idempotent; timestamp edit moves sample; complete→unknown removes prior sample; delete never touches another app's data. These are required device/failure-injection evidence, not claims already proven.

## 10. Backup/security policy proposal and remaining gates

Default private files: complete file protection, defer work while locked; protect DB/WAL/SHM/index/temp/pins. Propose exclusion of all private stores from automatic device/cloud backup pending Apple rules and physical verification, with user-initiated encrypted export to an explicitly chosen local destination. No custom cipher; A19 must select reviewed authenticated-encryption and password KDF design, archive format/version and resource limits before shipping. Contract does not choose cryptography without review. Backup includes IDs/revisions, overlays, custom foods, pins, log snapshots, settings, ledger/outbox/tombstones, schema/calculation versions, integrity and archive UUID; index/catalogue replaceable except retained dependencies. Restore empty diary only, all-or-nothing, repeated archive detection, Health hold. OS backup exclusions, destination behavior, protection after restart and SQLite sidecars must be measured on devices. This is a proposed conservative policy, not verified App Review compliance.

## 11. Portable wire baseline

UTF-8 JSON; keys lowerCamelCase; unknown keys ignored only within same supported schema major; unknown enum tags fail validation/quarantine rather than default. Required keys never omitted. Optional fields encode null (absence); empty collections encode []/{}. Decimal string grammar: 0 or positive integer, optionally '.' and 1–9 fractional digits; no exponent, plus sign, leading zeros, comma, negative zero or whitespace. Maximum 12 integer digits; calculations must reject inputs/intermediates outside agreed bounds rather than wrap. Canonicalize trailing fractional zeros away; nine fractional digits is storage precision, intermediate precision at least 38 significant decimal digits, final persistence rounding half-even once to nine places. A05 must validate this precision against realistic fixtures before freeze. Revision counters on wire are decimal integer strings to avoid JSON numeric interoperability loss. UUIDs lowercase hyphenated strings. Generation IDs are UUID strings assigned once per manifest; SHA-256 digests lowercase 64-character hex, separate from generation ID.

Implementation review amendment: public D02 ingestion rejects all unknown fields to prevent accidental inclusion of private or unsupported payloads; extending its leaf schema requires explicit review. Its synthetic evidence dictionary uses `kind`, `provenanceRef`, and `description`; density, portion and derived-input references resolve to same-provider evidence. Real-source evidence schemas remain deferred. The scaffold preserves every old immutable revision; garbage collection and rights-driven removal need a separate reviewed migration. A05 tests validate the 12+9 decimal boundary and final half-even policy; recurring division rounds within Foundation Decimal precision, while addition/multiplication precision loss is rejected. Fixture validation is not a substitute for the future production pack reader.

FoodID object: {"scope":"catalogue","namespace":"mealtracker.synthetic","recordID":"sausage"} or {"scope":"personal","uuid":"10000000-0000-4000-8000-000000000001"}. Field operations: {"op":"inherit"}, {"op":"clear"}, {"op":"set","value":...}; persisted overlay omits inherit operations after commit, while command encoding accepts it as reset. Nutrient encoding: {"status":"known","value":"200","unit":"kcal"}, {"status":"knownZero","value":"0","unit":"g"}, {"status":"unknown","reason":"notProvided","unit":"g"}, {"status":"trace","upperBound":null,"unit":"g"}, or derived with value/unit/methodID/inputRefs/estimated. Schema requires expected unit for nutrient key. Error envelope: {"code":"staleRevision","field":null,"details":{"expected":"1","actual":"2"},"retryable":false,"operationID":"..."}; details use code-specific typed schema, safe scalar IDs/counts only. Wire JSON examples are data specifications, not executable implementations.

Health review amendment: sample payload is immutable for each syncVersion, with retained payloadHash and monotonic high-water mark. Restore status explicitly reconciliationRequired. EU carbohydrate includes polyols and excludes fibre; public Apple description does not prove an equivalent definition, so mapping remains blocked. Export eligibility is separate from completeness. These conclusions match the Health research sibling; implementation still needs its exact API/device gates.

Final review amendments: earliest-authorized-date API must be guarded at iOS 27 per Health sibling's installed SDK evidence. Health sample batch save may be atomic within Health; there is still no transaction spanning private SQLite and Health. Per-type export eligibility explicitly includes semantic policy: sugar and fibre require a standalone export-policy decision when carbohydrate parent export is blocked; do not assume they automatically qualify. Energy/protein/fat eligibility proceeds independently. Source gates per D01: synthetic D02 permitted; SLV conditional; BLS acquisition/schema pending; OFF distribution review pending. Extend pack provenance with rawSHA256, termsEvidenceRef, reviewerDecision and distributionOfferURL at real-source ingestion; upstream dataset version must not be confused with API software version.

fixture-v1.json and fixture-v2.json are concrete minimal interchange data for D02/A05, limited to leaf foods. The Markdown fixture specifies recipes/private overlays/history and failure behavior. Required nutrient keys absent from a food map mean unknown(notProvided); consumers must materialize that status in domain projections. provenanceRef points to the envelope provenance map. retainedRevisions are immutable legacy records for pins, not active duplicate search hits. These minimal fixtures intentionally omit release-manifest checksums; D02 computes real output digests instead of shipping invented hashes.
